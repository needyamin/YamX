Overview

YamX (ymax) is a terminal-first coding and operations agent redesigned around a centralized routing system that dispatches every command — whether from CLI, REPL, web API, or future IPC channels — to the correct domain expert. It works entirely offline. AI providers are optional augmentations, not requirements.

Offline by Default

Every code path works with zero network and zero API keys. A NullProvider handles all AI requests gracefully when no keys are configured.

Router Is King

All input flows through Router.dispatch(). No direct expert calls from UI layers. The router classifies intent and extracts parameters before handing off.

Future-Proof AI

Adding a new LLM provider requires changes only in src/ai/. The router and experts remain untouched.

Dual Entry: The project preserves the original yamx CLI (legacy AI-agent mode in src/index.ts) while adding the new ymax router-based CLI (src/ymax.ts). Both share the same compiled output and toolset.

System Architecture

User Input → Router → Intent Classifier → Param Extractor

AI Orchestrator → Expert Registry → Domain Expert → Tool Execution

Data Flow

  1. Input Ingestion — CLI args, REPL line, or HTTP request is normalized into a RouteRequest.
  2. Intent Classification — Three-tier offline pipeline: exact pattern match → keyword TF-IDF scoring → Levenshtein fuzzy + history boost.
  3. Parameter Extraction — Regex-based entity extraction pulls file paths, URLs, ports, git refs, and package names into structured params.
  4. AI Decision Gate — AiOrchestrator decides whether to augment with AI based on confidence score and query complexity. Offline by default.
  5. Expert Dispatch — ExpertRegistry.resolve() returns the matched BaseExpert subclass.
  6. Workflow Execution — The expert runs its domain-specific workflow (e.g., validate paths → check permissions → backup → execute → verify).
  7. Result Rendering — Output is returned as string or structured JSON. Follow-up intents may be suggested.

Centralized Router

The router is the single entry point for all input vectors. It is completely decoupled from UI layers and AI providers.

RouteRequest Interface

interface RouteRequest {
  source: 'cli' | 'repl' | 'api' | 'web';
  rawInput: string;
  args?: Record<string, any>;
  sessionId?: string;
  cwd: string;
  userConfig: YamConfig;
}

RouteResult Interface

interface RouteResult {
  expert: string;        // target expert name
  intent: string;        // canonical intent label
  confidence: number;    // 0.0 – 1.0
  params: Record<string, any>;
  executionMode: 'direct' | 'interactive' | 'async';
}

Declarative Route Table

Routes are defined as data, not switch statements. Each route specifies patterns, keywords, target expert, intent, priority, and execution mode.

{
  name: 'file_read',
  patterns: ['read', 'cat', 'show', 'view', 'open'],
  keywords: ['read', 'file', 'show', 'view', 'content'],
  expert: 'filesystem',
  intent: 'read_file',
  priority: 85,
  executionMode: 'direct'
}

Intent Classification Pipeline

Tier 1: Exact Match

Direct string comparison against route patterns. First-token matching for high-priority routes. Score = 1.0.

Tier 2: Keyword Scoring

TF-IDF-style weighted overlap between user tokens and route keywords. Phrase matches score higher than single words. Normalized by input length.

Tier 3: Fuzzy + History

Levenshtein distance for typo tolerance. Historical success weights from ~/.ymax/intelligence-history.json boost previously successful routes.

Fallback

If top confidence < 0.4, route to GeneralExpert in interactive mode. It suggests the most likely commands.

Expert Module System

Each expert is a self-contained domain handler that extends BaseExpert and self-registers into the global ExpertRegistry on import.

BaseExpert Contract

abstract class BaseExpert {
  abstract readonly name: string;
  abstract readonly domain: string;
  abstract readonly capabilities: string[];

  abstract canHandle(intent: string, params: Record<string, any>): Promise<boolean>;
  abstract execute(intent: string, params: Record<string, any>, context: ExecutionContext): Promise<ExpertResult>;
  abstract getWorkflow(): WorkflowDefinition;
}

Expert Registry

Experts self-register using a side-effect import:

// src/ymax.ts
import './experts/filesystem.js';   // triggers: expertRegistry.register(new FilesystemExpert())
import './experts/shell.js';
import './experts/git.js';
// ...

Local Intelligence Layer

The IntelligenceEngine provides all offline reasoning capabilities. No API keys, no network.

Capabilities

  • Intent Classification — Fast-path exact commands, keyword mapping, and fallback detection.
  • Command Suggestions — Prefix matching with project-context boosts (e.g., npm projects get run npm test suggested).
  • Tool Ranking — Ranks the 32 available tools by relevance to the detected intent.
  • Output Summarization — Rule-based truncation at logical boundaries. Prioritizes error lines.
  • Entity Extraction — Regex patterns for files, URLs, ports, IPs, git refs, package names.

History Tracking

Every command execution is recorded in ~/.ymax/intelligence-history.json:

{
  "read_file": { "count": 12, "successes": 11, "failures": 1, "lastUsed": 1727830000000 },
  "run_command": { "count": 5, "successes": 4, "failures": 1, "lastUsed": 1727831000000 }
}

Success rate and recency are combined into a boost factor applied during fuzzy routing.

TF-IDF Embedding Engine

A lightweight vectorizer computes cosine similarity between user input and route definitions. If a heavier ONNX model (e.g., all-MiniLM-L6-v2) is added later, the interface stays the same.

AI Provider Abstraction

AI is an augmentation, not a requirement. The system is fully functional with the NullProvider.

Decision Rules (AiOrchestrator)

  1. If no provider keys are configured → skip AI entirely.
  2. If user passes --legacy or explicitly requests AI → use AI if available.
  3. If local intent confidence ≥ 0.85 → skip AI for speed.
  4. If confidence < 0.5 and AI is available → augment classification with AI.
  5. If query is complex (contains "explain", "debug", "refactor") → use AI.

Provider Adapter

The existing provider classes (OpenAIProvider, AnthropicProvider, etc.) are wrapped by ProviderAdapter to satisfy the new AiProvider interface:

// Register existing providers into the new orchestrator
const orchestrator = new AiOrchestrator();
if (cfg.providers.openai?.apiKey) {
  orchestrator.registerProvider(
    new ProviderAdapter(createProvider('openai', model, cfg))
  );
}
Key Design Principle: When a new LLM is released, only src/ai/ changes. The router, experts, and tool system remain untouched.

How to Implement / Extend

1. Add a New Route

Edit src/router/routes.ts and append to the routes array:

{
  name: 'my_feature',
  patterns: ['myfeature', 'mf'],
  keywords: ['myfeature', 'custom', 'plugin'],
  expert: 'myexpert',
  intent: 'run_my_feature',
  priority: 70,
  executionMode: 'direct',
  description: 'Run my custom feature',
  examples: ['myfeature', 'mf arg1'],
}

2. Add a New Expert

Create src/experts/myexpert.ts:

import { BaseExpert, ExpertResult, ExecutionContext, WorkflowDefinition } from './base.js';
import { expertRegistry } from './registry.js';

export class MyExpert extends BaseExpert {
  readonly name = 'myexpert';
  readonly domain = 'custom';
  readonly capabilities = ['do something cool'];

  async canHandle(intent: string) {
    return intent === 'run_my_feature';
  }

  async execute(intent: string, params: Record<string, any>, ctx: ExecutionContext) {
    return this.formatSuccess(`Executed ${intent} with params: ${JSON.stringify(params)}`);
  }

  getWorkflow() {
    return { name: 'custom', steps: [{ name: 'execute', description: 'Run it', required: true }] };
  }
}

expertRegistry.register(new MyExpert());

Then import it in src/ymax.ts:

import './experts/myexpert.js';

3. Add a New AI Provider

Implement AiProvider in src/ai/my-provider.ts, then register in src/ymax.ts:

import { MyProvider } from './ai/my-provider.js';
orchestrator.registerProvider(new MyProvider());

4. Add JSON Pattern Files

Drop new regex patterns into src/intelligence/models/. The ParamExtractor and IntelligenceEngine read them at runtime.

No rebuild of the router or existing experts is required. The architecture is designed so that additions are purely additive.
